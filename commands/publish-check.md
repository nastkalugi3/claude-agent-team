Проверь перед публичной публикацией проект: $ARGUMENTS
Если путь не указан, спроси, какой проект проверять.

Ничего не публикуй и не пушь. Это только проверка. Итог — вердикт «можно публиковать / после правок / нельзя».

1. **Что уйдёт наружу.** Если это git-репозиторий, смотри `git ls-files` и историю (`git log --stat`), иначе все файлы. Найди мусор: `.venv`, `__pycache__`, `.DS_Store`, `.ipynb_checkpoints`, модели и веса, базы, архивы, файлы больше 10 МБ, имена с кириллицей и mojibake (`#U0...`).
2. **Секреты.** Grep по файлам и истории: `sk-`, `ghp_`, `KGAT_`, `api_key`, `token`, `password`, `secret`, `.env`, `kaggle.json`, `access_token`. Значения не печатай, только файл и строку.
3. **Личные данные.** Абсолютные пути `/Users/...`, `/content/drive`, email, телефоны, имена. Метаданные: в `.ipynb` — `metadata.executionInfo`, `colab`, `userId`, `displayName`; в `.xlsx` и `.docx` — `docProps/core.xml` (creator, lastModifiedBy); в PDF — Author.
4. **Данные и лицензии.** Откуда каждый датасет, какая у него лицензия. Данные Kaggle-соревнований и данные заказчика публиковать нельзя без разрешения. Если лицензия неизвестна, рекомендуй убрать файл и дать скрипт загрузки.
5. **Правила площадки.** Для кода Kaggle-соревнования проверь, что соревнование уже закончилось (до конца приватно делиться кодом вне команды нельзя).
6. **Качество.** Запусти агента `code-reviewer` с задачей: README по стандарту (задача, данные, пайплайн, результаты с цифрами, как запустить, ограничения), цифры в README совпадают с файлами результатов, утечки данных, тесты проходят, ноутбуки по правилам оформления из CLAUDE.md. Агент работает только в папке проекта.
7. Пункты 1–5 сделай сам, параллельно с ревьюером.

Ответ: таблица «проверка — статус — что исправить», затем список блокеров, затем вердикт. Исправления не вноси без отдельного «да».
